## 1. 什么是 RAG

### 1.1 大模型的两个天生缺陷

GPT、DeepSeek 这类大语言模型(LLM)虽然强大,但有两个固有缺陷:

1. **会"幻觉"(hallucinate)**:知识不在它的训练数据里时,它会一本正经地编造。
2. **知识是"冻结"的**:它训练完那一刻的知识,之后的新文档、新知识它都不知道。

### 1.2 RAG 的思路

RAG(Retrieval-Augmented Generation,检索增强生成)的核心思想一句话:

> **回答之前,先从外部文档库里检索出相关的片段,把这些片段"塞进" prompt 里,让模型照着材料回答,而不是凭空回忆。**

```
用户提问
   │
   ▼
① 检索:从文档库里找出最相关的几个片段(chunk)
   │
   ▼
② 增强:把这些片段拼进 prompt,作为"参考资料"
   │
   ▼
③ 生成:LLM 依据参考资料作答(而不是只靠参数记忆)
```

这样做的效果:**把"闭卷考试"变成了"开卷考试"**。模型不再需要背下所有知识,只要能从给你的材料里找到答案即可——答案更准确、可溯源、可更新(换文档库就换了知识)。

### 1.3 本项目的完整链路

```
离线(建索引,一次):                         在线(问答,每次):
  文档(.md/.txt/.pdf)                       用户提问
     → 读文件、剥 frontmatter                  → 查询改写(多轮)
     → 切分成 chunk                           → 向量化查询
     → 向量化(embedding)                      → 混合召回(BM25 + 向量,RRF 融合)
     → 存盘(index/)                           → 交叉编码器精排
                                               → 拼 prompt(片段 + 历史)
                                               → LLM 流式生成
```

## 2. 核心概念入门

这一节把后面用到的每个概念都讲清楚,零基础也能看懂。

### 2.1 向量与 Embedding

**问题**:计算机不懂文字,模型只能算数字。怎么把"一段文本"变成"可计算的数字"?

**Embedding(嵌入)**就是答案:把一段文本映射成一个**固定长度的浮点向量**。比如本项目里,每个片段被映射成 **512 维**的向量:

```
"如何安装 DocOS?"  →  [0.012, -0.034, 0.058, ..., 0.021]   (512 个数)
```

**它凭什么有用?** 因为 embedding 模型是专门训练出来的,保证了一条性质:

> **语义相近的文本,在向量空间里距离也近。**

"怎么装 DocOS"和"如何安装 DocOS"字面不同,但向量很近;"如何安装"和"如何卸载"向量则相对远。于是"文本像不像"就变成了"向量近不近"——一个几何问题。

**模型内部怎么做**(以 BGE 这类编码器为例):

1. **分词(tokenize)**:把文本切成 token(中文按字/词,英文按子词);
2. **过 Transformer**:多层自注意力让每个 token 的表示被上下文影响;
3. **池化(pooling)**:把多个 token 向量合并成一个(取 `[CLS]` 或平均);
4. **归一化(normalize)**:把向量长度缩放到 1。

### 2.2 余弦相似度

判断两个向量有多"近",用**余弦相似度**:

```
cos(a, b) = (a · b) / (|a| · |b|)
```

直觉:**只看方向,不看长度**。两个向量方向越一致,值越接近 1;越正交越接近 0;方向相反接近 -1。

**关键优化**:如果所有向量都预先归一化(长度 = 1),分母就变成 1,于是:

```
cos(a, b) = a · b     (就是一个点积)
```

这带来一个巨大的好处:**一次检索可以写成一行矩阵乘法** `scores = V @ q`,其中 `V` 是 (N, 512) 的文档向量矩阵,`q` 是查询向量。GPU 上矩阵乘法极快。

### 2.3 向量检索 vs 关键词检索

| | 向量检索(语义) | 关键词检索(BM25,词法) |
|---|---|---|
| 原理 | 语义相近 → 向量相近 | 词是否精确出现 + 统计权重 |
| 擅长 | 同义改写:"怎么装"能命中"如何安装" | 精确词:错误码、函数名、ID |
| 短板 | 罕见标识符(如 `ERR_ZX_404`)在预训练里没有语义,向量抓不住 | 不懂"换个说法" |

结论:两者互补。真实系统里往往**两者都做,再融合**。

### 2.4 双编码器 vs 交叉编码器

这是理解"两阶段检索"的关键。

- **双编码器(bi-encoder)**:query 和文档**各自**编码成向量,再算相似度。快(文档向量可预先算好),但两者从不"互看",只能捕捉粗粒度的"语义相近"。
- **交叉编码器(cross-encoder)**:把 `[CLS] query [SEP] doc` **拼成一条输入**一起过一遍 Transformer,输出一个精确的相关性分数。准(能判断"是否真的回答了这个具体问题"),但每个 (query, doc) 对都要现算,无法预计算,慢。

所以工程上的经典做法是**两阶段**:先用快的双编码器从全库粗召回十几个候选,再用慢的交叉编码器对这十几个精排。

### 2.5 BM25

BM25 是信息检索里最经典的"词法匹配"排序公式,核心思想三条:

1. **IDF(逆文档频率)**:一个词在越少的文档里出现,越有区分度,权重越大;
2. **词频饱和**:一个词在本文档出现越多次,相关度越高,但有上限(不会无限加分);
3. **长度归一化**:长文档天然包含更多词,用平均文档长度校正。

它是纯统计的,不需要训练、不需要 GPU,对"精确关键词"极其可靠。

### 2.6 RRF(倒数排名融合)

混合检索要融合两个排序,但**两个分数尺度不可比**:向量余弦 ∈ [0,1],BM25 无上限。直接加权相加没意义。

RRF(Reciprocal Rank Fusion)只依赖**排名**而非**分数**:

```
rrf(d) = 1/(k + rank_向量(d)) + 1/(k + rank_BM25(d))
```

`k` 是常数(本项目用 60),`rank` 从 0 开始。一个文档在两份榜单里排名都靠前,RRF 分就高。它天然规避尺度问题、无需调权。

### 2.7 两阶段检索(汇总)

```
查询 → [粗召回] 向量 + BM25 → RRF 融合 → 取 top 12
     → [精排] 交叉编码器逐一打分 → 取 top 4
     → 送给 LLM
```

粗召回负责"别漏"(高召回率),精排负责"把最对的排前面"(高精确率)。

## 3. 整体架构

### 3.1 两条流水线

- **离线建索引**(`docrag index` / 上传文件时):把文档变成可检索的向量库。
- **在线问答**(`docrag ask` / web 聊天):查询 → 检索 → 生成。

两者通过**同一个 embedding 模型**连接——建索引和查询必须用同一个模型,否则向量不在同一个空间里,相似度没有意义。

### 3.2 目录结构

```
DocOS-rag/
├── pyproject.toml          # 依赖 + 命令入口(docrag / docrag-web)
├── config.yaml             # 所有可调参数
├── cli.py                  # 免安装入口
├── data/raw/               # 原始文档
├── index/                  # 生成的索引(可重建,gitignore)
├── src/docrag/
│   ├── config.py           # 读配置
│   ├── ingest/loader.py    # 多格式加载 + frontmatter 剥离
│   ├── ingest/chunker.py   # 切分
│   ├── embed/embedder.py   # 向量化 + 数 token
│   ├── store/index.py      # numpy 余弦检索
│   ├── store/metadata.py   # 持久化 + 增量 manifest
│   ├── retrieve/           # bm25 / retriever / hybrid / reranker
│   ├── generate/llm.py     # prompt + LLM 调用(多轮/流式/改写)
│   ├── engine.py           # RAGEngine:常驻状态 + 编排
│   ├── server.py           # FastAPI
│   ├── pipeline.py         # CLI 入口(委托 engine)
│   └── cli.py              # 命令行
├── frontend/               # Web 界面(原生 HTML/CSS/JS)
└── tests/                  # 单元测试
```

### 3.3 分层原则(面试可讲的"架构思想")

1. **接口隔离点只有两个**:`embedder.py`(向量化)和 `llm.py`(生成)。换模型只改这两个文件,其余层不动——这是"面向接口/依赖倒置"在 RAG 里的具体体现。
2. **索引是可重建的副产品**:原始文档是唯一真相,`index/` 随时能删掉重建,不应被当数据源。
3. **依赖注入**:`chunker` 需要的 `count_tokens`、`HybridRetriever` 需要的 embedder 都通过参数传入而非内部硬编码。它强制保证了"切分和向量化用同一个 tokenizer",也让单元测试能用假对象替代重模型。

## 4. 逐层详解(按数据流)

### 4.1 加载(loader)

**职责**:把不同格式的文件统一转成 `{source, title, text, meta}` 纯文本。

- `.md / .markdown / .txt`:读 UTF-8 文本,剥离 YAML frontmatter(用 PyYAML 解析,支持 `---` 和 `...` 闭合),提取标题(frontmatter 的 title → 第一个 H1 → 文件名)。
- `.pdf`:用 pypdf 抽**文本层**;扫描版(纯图片)需要 OCR,不在支持范围。

**设计点**:把"格式差异"隔离在 loader 一层,后面 chunker 不关心来源格式——这就是"统一抽象"。

### 4.2 切分(chunker)

这是本项目最细、也最容易踩坑的一层。分五步:

**(1) 按标题分节**。逐行扫描,遇到 `#`~`######` 标题就"落盘"上一节、开新节,维护 `heading_stack` 记录层级路径(如 `安装 > 使用 pip 安装`),存进 chunk 的 `section` 字段。标题是天然的主题边界,比等宽硬切好得多。

**(2) 节内区分代码块与正文**。` ``` ` 围栏内的代码作为**原子单元**,永不按句子切——技术文档的核心是代码,按句号切会把 `def f():` 劈得面目全非。

**(3) 句子切分**。正文按句切:
- 中文/ASCII 标点 `。！？!?；;` 直接切;
- 英文句号 `.` 只在"后面跟空白 + 大写字母/数字"时才切(避免误切 `e.g.`、`3.14`)。

**(4) 按 token 贪心合并**。用**模型自己的 tokenizer** 数 token,把句子一个个塞进当前 chunk,直到再加一句会超过 `chunk_tokens`(256)。为什么用 token 而非字符?因为模型的硬上限是 512 **token**;中文 1 字≈1 token,英文 1 长词≈1 token,两者不能混用。

**(5) overlap 重叠**。落盘时把当前 chunk 结尾、总 token ≤ `overlap_tokens`(32)的**正文句子**复制到下一 chunk 开头,防止把"一个完整意思"劈断。**代码不参与重叠**:代码按行切、行本身完整,且代码靠精确 token 检索,重复无益。

**兜底(硬切)**:单个单元本身超过 `chunk_tokens` 时(超长代码块/超长单句):代码按行切、英文按词切、中文按字符二分。这是"永不切开"的例外——当单元自己就超限时,只能切,但要尽量切在"行/词"边界而非"字"边界。

### 4.3 向量化(embedder)

- 用 `sentence-transformers` 加载本地模型 `BAAI/bge-small-zh-v1.5`(512 维)。
- `embed(texts)` 返回**归一化**的向量(于是余弦 = 点积)。
- `embed_query(text)` 给查询加前缀(部分 bge 模型是"非对称"的:查询和文档要用不同方式编码,查询侧要加指令前缀)。
- `count_tokens(text)` 用模型自己的 tokenizer 数 token,供切分用——这是"切分与向量化口径一致"的关键。

### 4.4 存储(index + metadata)

三个文件,都在 `index/`:

- `vectors.npy`:所有 chunk 的向量矩阵,形状 (N, 512),第 i 行 = 第 i 个 chunk;
- `chunks.json`:chunk 列表,每个含 `source`(文件路径)/`title`/`section`/`text`/`chunk_index`;
- `manifest.json`:每个文件的 SHA-256 内容哈希 + 当时的切分/模型配置(供增量)。

**关键关联**:`chunks.json` 里的 `source` 字段就是 chunk 和文件的连接线——删除、改名都靠它定位。

### 4.5 检索(retrieve)

**粗召回**:`HybridRetriever` 同时跑向量(BM25 各算一份排名,用 RRF 融合,取 `rerank_top_n`(12)个候选。

**精排**:`Reranker`(交叉编码器 `bge-reranker-base`)对这 12 个逐一打分,取 `top_k`(4)。

### 4.6 生成(generate/llm)

- `build_chat_messages`:把检索到的片段拼成上下文,加上 system 提示和历史,组成消息列表。
- **多轮对话**:服务器记住每个会话的 `[{role, content}]`,每次把历史一起发给 LLM。
- **查询改写**:多轮追问("那第二个呢?")本身没有可检索的语义,先用 LLM 把"历史 + 当前问题"改写成独立查询,再拿去检索;生成时仍用原问题 + 历史。
- **流式输出**:LLM 本来就是逐 token 生成的,流式只是把这个过程用 SSE 实时推给前端,打字机式显示。
- 支持 DeepSeek / OpenAI / Anthropic(通过 provider 分发,前两者是 OpenAI 兼容接口)。

### 4.7 增量索引(engine)

- 每个文件算 **SHA-256 内容哈希** + 记录切分/模型配置,存 `manifest.json`。
- 下次建索引时:**哈希和配置都没变 → 复用旧向量**(不重跑);变了 → 只重跑该文件;删了 → 自动移除。
- **改名检测**:路径变了但哈希没变 → 判定为改名,复用旧向量、只更新 `source`。
- 配置或切分代码版本(`CHUNK_VERSION`)变了 → 自动触发全量重建(否则旧规则下的 chunk 会被误复用)。

## 5. 设计决策汇总

| 问题 | 方案 | 为什么 |
|---|---|---|
| 文档太长不能直接给模型 | 切成 chunk | 模型 token 上限;一个向量表达一个主题;检索粒度 |
| 切分边界 | 按标题 + 句子 | 标题是主题边界,句子避免劈断语义 |
| 计量单位 | token 而非字符 | 模型限制是 token,中英文 token≠字符 |
| 边界语境丢失 | overlap | 复制结尾句子到下一 chunk 开头 |
| 代码被劈坏 | 代码块原子化 + 超长按行硬切 | 技术文档核心是代码 |
| 相似度计算慢 | 归一化 | 余弦退化为点积 = 一次矩阵乘法 |
| 精确关键词检索不到 | 加 BM25 | 向量不擅长错误码/函数名 |
| 两个分数尺度不可比 | RRF | 只依赖排名,无需调权 |
| 粗召回不够准 | 交叉编码器精排 | 双编码器快而糙,交叉编码器准而慢,两阶段取长补短 |
| 每次全量重跑太慢 | 增量(哈希+配置签名) | 只重跑变更文件 |
| 改名导致重跑 | 哈希匹配改名 | 内容没变就不用重新向量化 |
| 本地跑不动大模型 | embedding 本地 + LLM 云端 | 小模型本地可跑,大模型走 API |

## 6. 技术选型说明

- **本地 embedding + 云端 LLM**:embedding 用小模型(免费、离线、可控),LLM 用大模型(本地 8G 跑不动)。也正好匹配:DeepSeek 没有 embedding 接口,只有生成接口。
- **numpy 而非 faiss**:numpy 点积是精确检索、足够几千片段、且代码透明便于学习;faiss 是近似最近邻(ANN),数据量大到几万以上才需要,接口可平滑替换。
- **FastAPI + 原生 HTML/JS**:前端无构建步骤、无 Node 依赖,一个项目搞定;FastAPI 是 Python 生态最顺手的 web 框架,原生支持异步流式(SSE)。
- **不用数据库**:单用户本地工具,文件系统 + 内存足够;多用户/海量数据时才上 SQLite 或向量数据库。
- **不用 Docker**:`.venv` 已提供依赖隔离;部署成服务/引入向量数据库时才值得。

## 7. 已知局限与改进方向

- **中文分词**:BM25 目前对中文是"逐字"切(没引入 jieba),对中文精确关键词匹配偏弱。
- **PDF 后处理**:PDF 提取的文本有行内断词(`utiliza\ntion`)、目录点线、缺空格等,需要后处理。
- **大规模检索**:numpy 精确检索是 O(N),上规模要换 faiss(ANN)。
- **元数据过滤**:`section`/`title` 已存但未用于过滤(如"只看某章/某版本")。
- **多知识库**:目前单库,未支持按库隔离。
- **查询改写开销**:每次追问多一次 LLM 调用,可加"按需改写"(先判断是否含代词)省掉无谓调用。
- **流式以外的体验**:尚无会话持久化(重启清空)、无 token 用量统计。

## 8. 核心概念速记

- **RAG** = 先检索、再把检索结果塞进 prompt、让模型照着回答(开卷考试)。
- **Embedding** = 文本 → 固定长度向量,语义相近 → 距离近。
- **余弦相似度** = 归一化后就是点积,检索 = 一次矩阵乘法。
- **混合检索** = 向量(语义)+ BM25(精确词)互补,RRF 按排名融合。
- **两阶段检索** = 双编码器粗召回(快) + 交叉编码器精排(准)。
- **增量索引** = 内容哈希 + 配置签名,未变复用、改了重跑、删了移除、改名只改 source。
- **架构思想** = 接口隔离(embedder/llm 可替换)、索引可重建、依赖注入(测试友好)。
